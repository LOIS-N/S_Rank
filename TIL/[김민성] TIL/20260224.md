# Web Rogue-Survivor / Random TD + P2P NFT Trading (Design & Research Notes)

> 목표: 뱀서라이크(웨이브 생존) 또는 랜덤 타워 디펜스(운빨+합성/강화) 웹게임을 제작하고,  
> 게임 플레이로 획득/강화한 아이템을 **P2P-NFT 기반으로 실시간 거래**할 수 있는 차별점을 만든다.

---

## 0. 핵심 결론(요약)

- **웹게임(뱀서류/TD)은 서버 부담이 낮다.** 대부분의 시뮬레이션은 클라이언트(브라우저)에서 처리한다.
- “NFT 실시간 거래”는 온체인만으로는 UX가 나오지 않으므로, **오더북(Off-chain DB) + 체인 이벤트 인덱서 + 실시간 푸시(WS/SSE)** 구조가 사실상 필수다.
- 로그라이크/서바이버 장르는 원래 “런 안에서 성장하고 리셋하는 재미”가 핵심이라, **거래로 출발 전투력을 올리는 방식은 재미를 붕괴(P2W 오해)시키기 쉽다.**
- 따라서 거래 가능한 아이템은 **전투력 직결(수직 강화)**보다,  
  **빌드 다양성/커스터마이즈(수평 요소)** 또는 **강화된 결과물의 ‘유니크성’**을 중심으로 설계해야 한다.

---

## 1. 도메인 조사(시장/장르 특성)

### 1.1 뱀서라이크(로그라이크-서바이버)

- 런(run) 기반: 0에서 시작 → 랜덤 선택 → 성장 폭발 → 죽으면 리셋.
- 공유 요소가 약함: 보통 기록/빌드/영상 공유가 전부라 “거래 필요성”이 자연스럽지 않음.
- 거래를 붙이려면 “거래할 가치”가 런 플레이에서 만들어지도록 시스템화가 필요.

### 1.2 랜덤 TD / 운빨 디펜스

- 짧은 판과 높은 반복성, 랜덤 소환/합성/강화의 즉각적 도파민.
- 웹/모바일로 재현이 쉬워 “웹게임 배포”에 적합.
- 강화/합성 루프가 이미 강하므로, “강화된 결과물의 유니크성 + 거래”를 연결하기 좋음.

---

## 2. 유사 서비스 조사 + 차별점

### 2.1 Web2(장르) 레퍼런스

- 랜덤 TD / 운빨 디펜스류: 랜덤 소환 + 강화/합성 + 웨이브 구조가 대중적으로 검증됨.
- 차이점: 대부분 플랫폼/계정 내부 자산이며, “유저 간 P2P 소유권 이전(지갑 기반)”이 핵심이 아님.

### 2.2 Web3(경제/거래) 레퍼런스

- Web3 게임/마켓 사례는 대체로:
  - 오더(판매/구매 의사)는 **오프체인 저장**
  - 체결(정산)만 온체인 실행
  - UI는 인덱싱 + 실시간 이벤트로 “실시간처럼” 보이게 함

### 2.3 우리 프로젝트 차별점(명확히 주장)

- 아이템을 단순 보유가 아니라 **강화 기능을 아이템마다 선택** 가능하도록 설계.
- 강화 수치/옵션이 아이템 단위로 **고유하게 저장**되어 희소성이 생김.
- 이 유니크 아이템을 **지갑 기반 P2P-NFT로 실시간 거래** 가능하게 함.
- 웹에서 즉시 플레이 가능한 “짧은 판/빠른 회전” 장르에 적용.

## 3. 왜 블록체인이어야 하는가?

### 핵심 주장 3줄

1. **Ownership:** 강화된 아이템이 “계정 DB”가 아니라 **지갑 자산**이 된다.
2. **Transfer:** 운영자 중개 없이도 **P2P 소유권 이전**이 가능하다.
3. **Verifiability:** 아이템의 **고유 강화 수치/옵션을 위변조 어렵게 증명**할 수 있다.

### 현실적 원칙(중요)

- 블록체인은 “로그인/세션/프로필 DB”가 아니다.
- 실제 서비스는 **온체인(소유권/거래) + 오프체인(DB/오더북/게임 상태)** 하이브리드가 된다.

---

## 4. 사용자 참여 유도(웹게임 → 아이템 획득 → NFT 거래 구조)

### 4.1 기본 원칙

- 거래를 강요하지 않는다: **지갑 없이도 플레이 가능(옵트인 Web3)**.
- 게임만 해도 재미가 완결되어야 한다.
- 거래는 “플레이의 결과물”로 자연스럽게 따라오게 한다.

### 4.2 추천 루프

1. 런/웨이브 플레이
2. 재료/베이스 아이템 드랍
3. 합성/강화(옵션 선택형 강화)
4. (선택) NFT화/마켓 등록
5. P2P 체결 및 소유권 이전
6. 다시 플레이(시즌/도전/수집)

### 4.3 P2W 오해 방지

- 전투력 직결 아이템 거래만 열면 밸런스 붕괴 가능성이 높음.
- 거래 가치를 “수평 요소(다양성/커스텀/희소 옵션)”로 이동:
  - 스킨/이펙트/연출
  - 플레이스타일을 바꾸는 모듈/룬/보석(상황별 유불리)
- 경쟁/랭킹 모드는:
  - 표준화 룰 / 거래 아이템 제한 큐로 분리 운영 고려.

## 5. 시스템 설계(온체인/오프체인)

### 5.1 “블록체인 로그인” 개념

- 지갑 서명 기반 인증:
  - 서버 nonce 발급 → 유저가 nonce 서명 → 서버 서명 검증 → JWT/세션 발급
- 프로필/게임 진행은 DB(오프체인)에 저장하고,
  NFT는 소유권/거래 기록 중심으로 온체인에 남긴다.

### 5.2 NFT 모델 옵션(강화 수치 ‘고유 저장’ 중심)

#### 모델 A: ERC-721 (강화 완료 아이템 = 유니크 NFT)

- 아이템 단위 유니크 속성 저장에 직관적.
- 단점: 민팅/업데이트 비용(가스) 관리가 필요.

#### 모델 B: ERC-1155(베이스) + 강화 모듈(721/1155) 조합

- 베이스 아이템은 대량 관리(저렴), 강화/옵션은 모듈로 분리.
- 거래는 모듈 중심으로 돌려 P2W 완화 가능.

#### 모델 C: 오프체인 강화 + 온체인 스냅샷 해시

- 강화/옵션은 DB에 저장하되, 거래 시점에 상태 해시를 포함해 위변조를 줄임.
- 실서비스 성능/UX에 강함.

## 6. “실시간 거래”를 만들기 위한 필수 구성요소

> 온체인만 보면 블록 확정 지연 때문에 UX가 느리다.  
> 따라서 오더북/인덱싱/실시간 푸시가 필요하다.

- **Orderbook API + DB**
  - 서명 주문 저장/검색/정렬/취소
- **Indexer**
  - Transfer/Trade 이벤트 수집 → DB 반영
- **Real-time Push**
  - WebSocket 또는 SSE로 “새 리스팅/체결” 즉시 반영
- **Cache**
  - 소유권/메타데이터 조회 폭탄 방지(Redis)

---

## 7. 기술 스택(권장)

### 7.1 Frontend (Web Game)

- Engine: PixiJS or Phaser (WebGL)
- Wallet: MetaMask
- Web3 Integration: ethers.js / web3-react
- Performance: object pooling, sprite atlas, spatial hashing collisions

### 7.2 Backend

- Auth: nonce + signature verification + JWT/session
- Game API: progress/inventory/enhancement management
- Market API: orderbook endpoints
- Indexer: chain events -> DB sync
- DB: PostgreSQL
- Cache: Redis
- Real-time: WebSocket/SSE

### 7.3 Smart Contracts

- Items: ERC-721 or ERC-1155 (+ modules)
- Marketplace: signed orders + on-chain fulfill
- Metadata: IPFS/HTTP + hash/verification

---

## 8. 인프라/용량 가이드(초기 런칭 기준)

> 웹게임 시뮬레이션은 클라이언트 중심이므로 서버는 “API/마켓/인덱서/DB”가 핵심 부하.

- Static hosting: Cloudflare + S3 (or Nginx)
- API + Orderbook:
  - 2–4 vCPU / 4–8GB RAM (초기)
- DB (Postgres):
  - 2 vCPU / 8GB RAM / SSD 100–200GB (초기)
- Redis:
  - 1 vCPU / 1–2GB RAM
- Indexer:
  - 1–2 vCPU / 2–4GB RAM
- Real-time server (WS/SSE):
  - API 서버와 분리 가능(트래픽 증가 시)

---

## 9. 리스크 & 주의사항

- “강화+거래”는 작업장/매크로 유입 및 경제 인플레 리스크가 큼.
- 플랫폼 정책(예: 유통 채널별 Web3 제한) 가능성 고려 필요.
- 승인(approve)/서명 피싱 UX 대응 필수:
  - 최소 권한, 경고 UI, 도메인 고정, nonce/expiry 적용
- 완전 온체인 고집은 비용/복잡도/UX 리스크가 커서, 하이브리드가 현실적.
